# Hearth hosting protocol

The packaged `Hearth.Host.exe` is an ASP.NET Core executable owned by the launcher. Hearth starts and monitors its local host while the app is open or in the system tray; fully exiting Hearth stops it. Fresh hosts store data inside the current profile's `Host` directory and do not install a Windows service. The installer retires any legacy `HearthHost` service before upgrading, preserving its registered data path, port, releases, members, and credentials. A one-time protected `%PROGRAMDATA%\Hearth\retired-host.json` descriptor identifies the original Windows user and existing data for launcher adoption. Development and integration tests can still start the host directly.

Initialize once with `--init --data <directory> --owner-token-file <file> [--port 17842]`. The file must contain a cryptographically random owner credential of at least 32 characters. Initialization stores only its SHA-256 hash in `host.json` and refuses to overwrite an existing host. Delete the temporary credential file after the launcher saves the credential. Run with `--data <directory>` afterward; `--port` overrides the stored port. `--bind` overrides the stored IP address. The safe HTTP default is `127.0.0.1`. The launcher always binds management there and optionally adds `--https-port 17843` for direct encrypted sharing on IPv4 interfaces. Do not forward the plaintext port. The host does not trust forwarded client-IP headers.

All protected routes use `Authorization: Bearer <credential>`. Credentials belong either to the host administrator or to an individual membership in one pack. Member credentials are generated by the host, returned once, and stored only as hashes. An invite creates a pending membership; it never grants download access. Display names are self-selected, so owners should verify the displayed fingerprint with their friend before approving an unfamiliar request.

| Method and route | Permission and result |
| --- | --- |
| `GET /health` | Public service identity and current UTC time. No pack details. |
| `GET /owner/packs` | Administrator gets all active packs; delegated owner gets only their owned pack. Each summary includes `pendingCount` and `sharedInviteEnabled`. |
| `POST /owner/packs` | Administrator creates a pack from `CreatePackRequest`. |
| `GET /owner/status` | Administrator gets approved-player access evidence since service start. |
| `GET /owner/endpoints` | Administrator gets the host's advertised Internet and home-network addresses and certificate pin. |
| `POST /packs/{id}/join` | Valid invite code creates a pending membership and returns its credential once. Limited to 15 requests per minute per connecting IP. |
| `GET /packs/{id}/access` | Membership holder checks `pending`, `approved`, `removed`, or `archived` state. Administrator is approved for active packs and receives `archived` for archived packs. |
| `GET /packs/{id}/members` | Pack owner sees active names, roles, request times, credential fingerprints, and optional personal-invite labels. |
| `PATCH /packs/{id}/members/{memberId}` | Pack owner approves/removes players. Omitted or null `role` preserves the existing role. Only administrator may grant/change owner privileges or change an owner membership. |
| `POST /packs/{id}/members/decline-all` | Pack owner marks pending players removed; approved members are unchanged. Returns `{count}`. Only the administrator can affect pending owner memberships. |
| `DELETE /packs/{id}/invite` | Pack owner resets the shared invite code and receives the updated pack summary. Already-approved memberships and personal invites remain valid. |
| `PATCH /packs/{id}/invite` | Pack owner sends `{enabled: true/false}` to enable or disable the shared invite. Returns the updated pack summary. |
| `GET /packs/{id}/invites` | Pack owner lists personal invite records, including codes and used/revoked status. |
| `POST /packs/{id}/invites` | Pack owner creates a personal invite with `{label, singleUse, expiresAt}`. Approval remains required. |
| `DELETE /packs/{id}/invites/{inviteId}` | Pack owner revokes a personal invite; approved members keep access. Returns the revoked record. |
| `POST /packs/{id}/archive` | Administrator moves the whole pack into the host's archive directory. Delegated owners cannot archive. Returns `{packId, name, archivedAt}`. |
| `PUT /packs/{id}/blobs/{sha256}` | Pack owner uploads a raw JAR; hash, size, and ZIP directory are checked before commit. |
| `POST /packs/{id}/releases` | Pack owner publishes a complete `PublishRequest`; `expectedReleaseId` provides optimistic concurrency. |
| `GET /packs/{id}/manifest` | Approved member/owner receives the latest complete release. |
| `GET /packs/{id}/releases/{releaseId}/manifest` | Approved member/owner receives one complete historical release in this pack; used to compare a saved draft with its original release. |
| `GET /packs/{id}/blobs/{sha256}` | Approved member/owner downloads content published in this pack. HTTP ranges are supported. Knowing another pack's hash gives no access. |

Files are managed directly under `mods/`, with Windows-safe JAR filenames. The group is `base`, `voxy`, or `distanthorizons`. Base files are selected for every player. Optional dependencies belong to the corresponding optional group; a shared dependency may appear in both groups with the same path and hash. A dependency also needed by the base pack belongs to `base`. Conflicting base/optional content at one path is rejected. Voxy and Distant Horizons are mutually exclusive selections and can offer different content at the same path.

The launcher and host use the same mod-ID validation for each playable combination (Required only, Required + Voxy, Required + Distant Horizons). An optional resolver skips dependencies whose IDs are already provided by Required mods. A conflicting duplicate is rejected locally before uploads and is checked again by the host before publication. Keep shared dependencies in Required mods so Off players retain them.

The host limits each uploaded JAR to 512 MiB, a release to 2,000 entries and 16 GiB, and release notes to 4,000 characters. Release files and hashes are revalidated before the current-release pointer is atomically replaced. Old complete releases remain downloadable for clients already synchronizing them. Removing a membership denies subsequent metadata/download requests immediately; bytes already transferred cannot be recalled. Host owners must keep backups of the entire host data directory. Releases and blobs are retained; automatic garbage collection is not performed.

## Membership, invites, and archives

All additions use the existing JSON conventions (camelCase field names and UTC ISO timestamps). Older summaries without the new fields default to `pendingCount: 0` and `sharedInviteEnabled: true`. Existing shared invite URLs and `JoinRequest {inviteCode, displayName}` remain valid. A personal invite code uses that same request and the same `hearth://join` format; no new join endpoint or bearer token is needed.

`CreatePersonalInviteRequest` accepts a nonempty `label` of at most 80 characters, optional `singleUse` (default true), and optional future `expiresAt` (null means no expiry). The response and list entries contain `id`, `label`, `code`, `singleUse`, `expiresAt`, `createdAt`, `usedAt`, and `revoked`. A single-use code is consumed atomically when its first valid pending request is saved, not when the owner approves it. Reusable invites record their latest use. Expired, consumed, revoked, disabled, or replaced invite codes return 404 and create no membership. Turning off the shared invite does not disable personal invites. Resetting a shared invite does not enable a disabled shared invite.

Member records add nullable `inviteLabel` and `inviteId`. The label is the owner's text, distinct from the player's self-selected display name. These fields are for request context, not proof of identity. The People view groups display names and invite labels for presentation only: credentials and permissions remain scoped independently to each pack. Inviting an existing member to another pack creates a new personal invite there; it does not automatically grant access.

`MemberUpdate` accepts `{status, role?}`. The role can be `player` or `owner`; omitted/null means retain the current role. `status` can be `pending`, `approved`, or `removed`. Removed members are hidden from the member list but retained as tombstones so their saved credential receives an explicit removed status. At most 2,000 active members/requests are allowed per pack; new requests retain the latest 2,000 removed records. Personal invites allow at most 1,000 currently usable codes, retaining up to 2,000 inactive records when new ones are created. Owners can decline spam without permanently exhausting those active limits. The launcher refreshes owner counts about every 60 seconds and pending-player approval about every 30 seconds while the relevant views are active.

Archiving moves `packs/<id>` to `archive/<id>` and writes `archive-info.json`, preserving releases, blobs, membership records, and invite history. Archived packs disappear from owner lists. Existing members and the administrator receive `status: archived` through `/access`; unknown credentials still receive 403. Other pack operations return 410 for an archived pack and cannot publish, join, or download it. The archive route is administrator-only, even if the caller owns that pack as a delegated member. There is no hard-delete or archive-restore API.

Protected routes require a bearer credential (401 if absent); an insufficient credential returns 403. Unknown packs/releases and invalid invite codes return 404; archived packs return 410; publication conflicts return 409. Responses contain an `error` string. Each route enforces the relevant pack authorization in the host, including historical manifests and blob downloads. Invite codes only request membership and are never accepted as download credentials.

`/owner/status` returns `startedAt`, `lastPlayerAccessAt`, `lastPlayerName`, `lastPackName`, `lastOperation`, and `successfulPlayerRequests`. This records successful approved-member requests, not anonymous health probes. It also returns `lastInternetPlayerAccessAt` and `lastInternetPlayerName` when an approved request arrives over HTTPS from a directly observed public IPv4 address. These fields do not trust forwarded headers; LAN, loopback, anonymous, pending and removed members do not establish outside-access evidence. IPv6 and external reverse-proxy paths are conservatively unconfirmed. A past request does not guarantee future availability or prove that a complete download finished.

Developer security check: build the host in Release with the .NET 10 SDK (`dotnet build src/Hearth.Host -c Release`), then run `python tests/host_security_smoke.py`. The test prefers the workspace SDK at `tools/dotnet/dotnet.exe` when present. It launches temporary real hosts and checks private-pack isolation, forwarded invites, role scoping, invalid publish rejection, duplicate mod identities, atomic release preservation, and revocation across restart.

## Direct HTTPS and connection links

`Host/host-tls/identity.pfx` stores the host certificate and private key. On Windows its directory and file ACL allow only the hosting Windows user and SYSTEM. Back it up with the rest of the host data. Loading a corrupt, expired, or missing existing identity fails with recovery guidance; it is not silently rotated. Windows uses a temporary per-user native key for Schannel and removes it when the certificate is disposed, without installing a root certificate or trust exception.

A connection link has the form `hearth://host?host=<escaped-https-address>&pin=<sha256-certificate>&id=<host-id>`. It deliberately excludes owner credentials. A pack invite uses `hearth://join?host=...&pack=...&code=...&pin=...&id=...`. The HTTPS callback validates the exact SHA-256 certificate and validity period before sending application credentials; automatic redirects are disabled. Plain HTTPS URLs retain normal platform certificate validation. Saved trust cannot be downgraded by omitting a pin, and a new pin cannot replace an already trusted endpoint without forgetting that saved connection.

The launcher creates a narrowly scoped firewall rule for the host executable and HTTPS TCP port with explicit Windows elevation. Automatic startup only checks that rule; it never requests elevation. NAT-PMP/UPnP setup uses the detected gateway, avoids unrelated mappings, renews leases and checks for endpoint changes. UPnP control requests are restricted to the gateway's literal IP with bounded parsing and timeouts. A router mapping is configuration evidence, not a reachability probe. Router ownership checks and cleanup never authorize changing unrelated rules.

The owning launcher atomically writes `advertised-endpoints.json` in the host data directory whenever sharing addresses change, and withdraws them when hosting stops. `/owner/endpoints` returns `{hostId, certificatePin, internetAddress, homeNetworkAddresses, updatedAt}`. A missing, malformed, oversized, or wrong-host advertisement yields an empty address list and null Internet address/pin. Remote managers check the returned host identity and pin against their trusted connection before using these addresses for invites. This enables a manager connected over the home network to copy the host's Internet invite. DNS, dynamic DNS, and VPN HTTPS addresses are supported by exact certificate pinning; they do not require a new certificate. The user must route any manually supplied address to the host.

The launcher listens for Windows network-address changes, retries setup with backoff, and retries lost router leases. UPnP tries a bounded range of external ports so another Hearth PC can retain its own mapping. A retry checks Windows firewall permission before restarting any listener, preserving a working host if the permission prompt is canceled. HTTP connection establishment is limited to eight seconds. Launcher metadata operations have a 20-second deadline; release publication and file transfer can take longer, with cancellation supported. Redirects remain disabled so credentials cannot follow a changed destination.

`JoinedPack.InstanceHostUrl` preserves the installation's original storage identity while `HostUrl` changes to a verified replacement endpoint. A cross-address reconnect requires the same certificate, host identity, and pack; the local host owner's existing protected identity permits migration from localhost as well. This keeps the original Prism instance, approval and player preferences. Internet address discovery does not provide DNS or a global rendezvous service.

A verified replacement address updates all saved pack and owner connections with that same host ID and certificate pin. Installed records also retain `hostId` and `certificatePin`, allowing a removed pack to find its original instance when it is rejoined through a different address. Legacy instance folders remain valid; records without a verified identity are never matched to an unrelated host by name alone. Delegated owner connections group packs for navigation but resolve each pack's own credential before an owner request.
