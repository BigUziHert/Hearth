# Hearth hosting protocol

The packaged `Hearth.Host.exe` is an ASP.NET Core executable owned by the launcher. Hearth starts and monitors its local host while the app is open or in the system tray; fully exiting Hearth stops it. Fresh hosts store data inside the current profile's `Host` directory and do not install a Windows service. The installer retires any legacy `HearthHost` service before upgrading, preserving its registered data path, port, releases, members, and credentials. A one-time protected `%PROGRAMDATA%\Hearth\retired-host.json` descriptor identifies the original Windows user and existing data for launcher adoption. Development and integration tests can still start the host directly.

Initialize once with `--init --data <directory> --owner-token-file <file> [--port 17842]`. The file must contain a cryptographically random owner credential of at least 32 characters. Initialization stores only its SHA-256 hash in `host.json` and refuses to overwrite an existing host. Delete the temporary credential file after the launcher saves the credential. Run with `--data <directory>` afterward; `--port` overrides the stored port. `--bind` overrides the stored IP address. The safe default is `127.0.0.1`; expose it using an HTTPS reverse proxy or HTTPS tunnel, not by forwarding the plaintext port. The host does not trust forwarded client-IP headers.

All protected routes use `Authorization: Bearer <credential>`. Credentials belong either to the host administrator or to an individual membership in one pack. Member credentials are generated by the host, returned once, and stored only as hashes. An invite creates a pending membership; it never grants download access. Display names are self-selected, so owners should verify the displayed fingerprint with their friend before approving an unfamiliar request.

| Method and route | Permission and result |
| --- | --- |
| `GET /health` | Public service identity and current UTC time. No pack details. |
| `GET /owner/packs` | Administrator gets all packs; delegated owner gets only their owned pack. |
| `POST /owner/packs` | Administrator creates a pack from `CreatePackRequest`. |
| `GET /owner/status` | Administrator gets approved-player access evidence since service start. |
| `POST /packs/{id}/join` | Valid invite code creates a pending membership and returns its credential once. Limited to 15 requests per minute per connecting IP. |
| `GET /packs/{id}/access` | Membership holder checks their approval state; administrator is always approved. |
| `GET /packs/{id}/members` | Pack owner sees names, roles, request times, and credential fingerprints. |
| `PATCH /packs/{id}/members/{memberId}` | Pack owner approves/removes players. Only administrator may grant/change owner privileges. |
| `DELETE /packs/{id}/invite` | Pack owner rotates the invite. Already-approved memberships remain valid. |
| `PUT /packs/{id}/blobs/{sha256}` | Pack owner uploads a raw JAR; hash, size, and ZIP directory are checked before commit. |
| `POST /packs/{id}/releases` | Pack owner publishes a complete `PublishRequest`; `expectedReleaseId` provides optimistic concurrency. |
| `GET /packs/{id}/manifest` | Approved member/owner receives the latest complete release. |
| `GET /packs/{id}/blobs/{sha256}` | Approved member/owner downloads content published in this pack. HTTP ranges are supported. Knowing another pack's hash gives no access. |

Files are managed directly under `mods/`, with Windows-safe JAR filenames. The group is `base`, `voxy`, or `distanthorizons`. Base files are selected for every player. Optional dependencies belong to the corresponding optional group; a shared dependency may appear in both groups with the same path and hash. A dependency also needed by the base pack belongs to `base`. Conflicting base/optional content at one path is rejected. Voxy and Distant Horizons are mutually exclusive selections and can offer different content at the same path.

The host limits each uploaded JAR to 512 MiB, a release to 2,000 entries and 16 GiB, and release notes to 4,000 characters. Release files and hashes are revalidated before the current-release pointer is atomically replaced. Old complete releases remain downloadable for clients already synchronizing them. Removing a membership denies subsequent metadata/download requests immediately; bytes already transferred cannot be recalled. Host owners must keep backups of the entire host data directory. Releases and blobs are retained; automatic garbage collection is not performed.

`/owner/status` returns `startedAt`, `lastPlayerAccessAt`, `lastPlayerName`, `lastPackName`, `lastOperation`, and `successfulPlayerRequests`. This records successful approved-member requests, not anonymous health probes. It deliberately does not claim a request originated outside the LAN. Confirm external access by asking an approved friend on another network to press Play and checking that the timestamp advances.

Developer security check: build the host in Release with the .NET 10 SDK (`dotnet build src/Hearth.Host -c Release`), then run `python tests/host_security_smoke.py`. The test prefers the workspace SDK at `tools/dotnet/dotnet.exe` when present. It launches temporary real hosts and checks private-pack isolation, forwarded invites, role scoping, invalid publish rejection, duplicate mod identities, atomic release preservation, and revocation across restart.
